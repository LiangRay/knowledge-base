# 论文笔记：Expert Coupling in MoE Pretraining — 用相关性摆放专家 + 提前搬 Token 来减少 All-to-All

- **论文**：Expert Coupling in MoE Pretraining: Reducing All-to-All Overhead with Correlated Placement and Token Shuffling
- **arXiv**：[2610.09372](https://arxiv.org/html/2610.09372)（2026-10-07，cs.CL，CC BY 4.0）
- **作者**：Radha Gulhane、Quentin Anthony、Beren Millidge（Zyphra）
- **实现**：Megatron-LM；硬件 AMD Instinct MI300X（每节点 8 卡，节点内 xGMI 全互联，节点间 8×100Gb/s RoCE）

---

## 一句话总结

MoE 预训练进行不久，路由器选专家就已经有**稳定的规律**：同一层里某几个专家经常一起被选；这一层选了谁，基本能猜到下一层会选谁。论文利用这两种规律，让 token 和它要用的专家尽量待在同一张 GPU 上。**A2A 时间缩短 1.16–2.63×，整个训练 step 最多快 1.41×**。**路由结果、专家参数和 loss 都不变。**

---

## 1. 问题：EP 下 All-to-All 太贵

- EP 把专家分到不同 GPU 上。每个 MoE 层前向要做 dispatch + combine 两次 A2A，反向再做两次。
- 通信量随 **EP 规模**和 **top-k** 增长。token 的专家落在本卡的比例约为 1/EP，top-6 的通信量是 top-2 的 3 倍。EP 一旦跨节点，节点间的慢链路就成了主要耗时。
- 实测（Megatron 原生 A2A dispatcher + 连续摆放）：

| A2A 占 step 时间 | EP8 | EP32 |
|---|---|---|
| top-2 | 13.5% | 44.8% |
| top-6 | 24.0% | **60.4%** |

EP32 + top-6 时，A2A 的耗时比专家计算和所有非 MoE 计算加起来还多。

- 目前的做法（专家副本、SmartMoE 按负载搬专家、MoonEP 动态冗余专家等）主要解决**负载倾斜**：把通信摊开，降低最忙链路的峰值。但**总通信量基本没变**，副本还要额外占显存。DeepSeek-V3 的 node-limited routing 能减少跨节点流量，代价是**改了路由**。
- 默认摆放方式：expert e 放在 GPU ⌊e / (E/EP)⌋ 上（连续摆放），完全不考虑哪些专家经常被一起使用。

## 2. 关键发现：路由有两种相关性

### ① 层内相关（co-selection）
- 以 top-2、第 8 层为例：8,128 种专家组合里，**64 对（0.8%）承载了 42% 的 token**。如果路由彼此独立，这 64 对只会占 1.6%。
- 14 对专家的条件共选概率 ≥50%，合计承载 16% 的 token。
- 128 个专家里有 73 个，各自都有一个"搭档"出现在它 ≥30% 的 token 里。
- 在去重 dispatcher 下，把一对高频共选的专家放在同一张卡上，这对专家的流量减半。

### ② 跨层相关
- 第 8 层的 128 个专家中，112 个会把 ≥30% 的 token 送到第 9 层的**同一个**专家，中位数是 48%。
- 所以在 layer ℓ+1 的 router 运行之前（中间还隔着一整个 attention block），就能预测 token 下一层的专家会落在哪张 GPU 上。

### ③ 稳定性（这是能用在预训练上的前提）
- 大约 **1B token** 后规律就形成了：
  - step 199 拟合的表，已能拿到最终收益的一半左右（top-2 EP8 去重 14.4%，最终为 26.5%）；
  - step 1000 拟合的表，与最终值只差 2–3 个百分点；
  - step 1400 之后拟合的表，和训练结束时几乎一样（相关系数 > 0.93）。
- **几千个 token 就够拟合**：用 1,024 个 token 拟合的表，已能去掉 23.6%（top-2）/ 57.9%（top-6）的行。用 4,096 个 token 拟合的表，与 held-out 数据的 Pearson 相关系数是 0.93 / 0.98，效果和用全部 524k token 拟合的差距不到 1 个百分点。**一个 microbatch 就够**。
- 建议每 ~1000 step 重新拟合一次，每次只需一个 microbatch 的路由记录。
- 预测器命中率：相关性形成前约 12.7%（接近随机水平 12.5%），step 1000 时 54%，step 1800 时 57%。

## 3. 方法一：Correlated Expert Placement + 去重 Dispatcher（适用于任意 EP 布局）

### 去重 Dispatcher（Dedup）
- Megatron 原生做法：token 选了几个专家就发几份 hidden state，哪怕这些专家在同一张卡上。
- 改法：每个 **(token, 目标 rank)** 只发一行，附带该 rank 上专家的 ID 和 gate 权重，接收方在本地展开并按专家分组做 grouped GEMM。元数据随 activation 一起发送，不需要额外的 collective。
- combine 时先在专家所在的 rank 上按 gate 权重加权求和，再回传一行 partial output。
- 这一技术本身来自 DeepEP，本文把它移植到了 Megatron，作为相关性摆放的基础。

### 相关性摆放
- 每层建一张共选图：W[e,e'] = 同时选中 e 和 e' 的 token 数。
- 用 **Kernighan–Lin 风格的两两交换**做均衡划分：从连续摆放出发，只要交换两个专家能提高"同卡共选权重之和"就交换，直到无法再提升或达到 I_max 次。全程只做交换，所以每张卡固定 E/EP 个专家，**专家参数占用的显存不变**。
- 跨节点时**分两级划分**：先按节点分（减少跨节点流量），再在节点内按 GPU 分。
- 结果是每层一个专家 ID 置换表，作用在 routing map 上。checkpoint 按全局专家 ID 存，**换一种摆放也能直接加载同一个 checkpoint**。

### 效果（实测）

| | 通信量减少（EP8 / 16 / 32 / 64） | A2A 时间加速 | Step 加速（EP8 / 16 / 32 / 64） |
|---|---|---|---|
| top-2 | 1.36× / 1.29× / 1.22× / 1.12× | 节点内 1.16×；跨节点 1.34× / 1.38× / 1.34× | 1.05× / 1.13× / 1.14× / 1.11× |
| top-6 | 2.36× / 1.95× / 1.54× / 1.24× | 节点内 1.58×；跨节点 1.95× / 1.48× / 1.35× | 1.14× / **1.41×** / 1.25× / 1.23× |

- 只开去重、不改摆放时，只能去掉碰巧落在同一卡上的重复行（EP8：top-2 6%，top-6 25%）。
- 👉 top-k 越大、越跨节点，收益越大。
- dispatch 和 combine 的字节数天然相同，所以通信量的减少对反向的两次 A2A 同样有效。

## 4. 方法二：Token Shuffling（仅适用于 TP=EP + Sequence Parallel）

**动机**：专家已经摆在一起了，但在 TP–EP 布局下，token 仍然待在"按序列位置分到的那张卡"上，专家在本卡的概率只有 1/EP。

**做法**：
1. Attention 之后本来就有一次 SP 的 **reduce-scatter**。论文在其中**融合一个置换**：把每个 token 直接送到"预测它下一层专家所在的 rank"（owner），残差流的那一行也一起搬过去，残差加法在新 owner 上完成。
2. MoE 之后的 **all-gather** 里再融合一个逆置换，恢复原来的 token 顺序（attention 依赖顺序）。
3. 因为 reduce-scatter / all-gather 本来就要搬运所有 token，改变谁去哪张卡只是改了索引，**不增加通信字节，也不增加额外的 collective**。两次融合置换每个 step 只多花几毫秒。

**Owner 预测器（Shuffle Planner）**：
- 离线统计表：用前两层的专家对 (e', e) 预测下一层专家在各 rank 上的分布（二阶表 S_m）；样本少时回退到只看前一层的单个专家（一阶表 F_m）。
- 每个 token 得到一个首选 owner 和一个置信度。SP 要求每个 rank 恰好分到 T/EP 个 token，所以按置信度从高到低，依次分给还有容量的首选 rank。
- 计划生成的开销约为前向 A2A 时间的 1/3，串行执行会抵消大部分收益。但计划只依赖第 i 层及之前的路由结果，到第 i+1 层的 reduce-scatter 才需要用到，所以 Planner 在 **side stream** 上运行，和专家计算、下一层 attention 重叠，最后用一次 event wait 汇合。主流每个 step 只多等约 1ms（0.02%）。
- Planner 需要的路由 ID 已经包含在 dispatcher 现有的元数据 all-gather 里。

**效果**：
- 本地命中率：
  - top-2：12.5% → **59%**（EP8），6.3% → 53%（EP16）；
  - top-6：12.5% → 57%（EP8），6.3% → 46%（EP16）。
- 跨网络字节（相对 baseline）：top-2 减少 2.4×（EP8）/ 2.1×（EP16），top-6 减少 **3.1×** / 2.4×。只做摆放时分别是 1.4× / 1.3× 和 2.4× / 1.9×。
- A2A 时间：
  - TP16EP16：top-2 从 1.55×（只做摆放）提升到 1.74×；top-6 从 1.95× 提升到 **2.63×**。
  - TP8EP8：top-2 1.40×，top-6 1.46×。
- ⚠️ 一个反直觉的结果：**单节点 top-6 加上 shuffling 后反而略差**（1.46× vs 只做摆放的 1.48×）。xGMI 是全互联，collective 的耗时由**最忙的那对 GPU** 决定，而不是总字节数。token 集中到一个 owner 后，总量降了，最热链路却更热了。
- 端到端：TP=EP 布局下 TP 自己的 collective 占了不少时间，A2A 占比变小（top-2 9–21%，top-6 18–38%），所以 step 加速只有：
  - top-2：1.01–1.06×；
  - top-6：1.08×（TP8EP8）、**1.34×**（TP16EP16，只做摆放时为 1.28×）。

## 5. 消融：不同负载均衡方式（top-6）

| Router | 最大/平均负载比 | Loss | 去重比例 EP8 / EP16 | Step 加速（TP1 EP16） |
|---|---|---|---|---|
| seq aux loss 1e-2（主模型） | 1.52 | 4.46 | 58% / 49% | **1.41×** |
| seq aux loss 1e-1（更强） | 1.20 | 4.64 | 51% / 40% | 1.30× |
| DeepSeek-V3 aux-loss-free | 1.37 | **4.39** | 47% / 36% | 1.26× |

- 三种 router 下都存在相关性，收益大小取决于各自共选结构的强弱。所有 EP16 布局上的加速都 ≥1.20×。
- 负载越均衡，实际节省的时间越接近节省的字节数（A2A 要等最忙的 rank）。
- 结论：本文针对的是**通信总量**，不是负载倾斜，可以和专家副本 / 按负载搬专家（SmartMoE、MoonEP、GRACE-MoE）叠加使用。

## 6. 实验设置（要留意的局限）

| 项目 | 取值 |
|---|---|
| 层数 | 12，每层都是 MoE |
| d_model / 注意力头 | 4096 / 16 头 × 32 维（attention 宽度 512） |
| 专家 | 128 个，FFN 1024，GELU，**无共享专家**，dropless |
| Router | FP32 linear，对全部 E 做 softmax 后取 top-k（k=2 或 6） |
| 参数量 | 总 13.6B；激活约 0.31B（top-2）/ 0.71B（top-6） |
| 训练 | FineWeb-Edu，序列长度 8192，global batch 128，**2000 step ≈ 2.1B token** |
| 精度 | BF16；router 和优化器状态用 FP32 |

- 只测了一个模型，且只训了 2.1B token，规模和训练长度都偏小。
- 硬件只有 AMD MI300X + RoCE，**没测 NVIDIA / NVLink / IB / EFA**。
- Token shuffling 要求 TP=EP，不支持 TP1；context parallel 和 EP 推理都没有评估。

## 7. 和相关工作对比

| 工作 | 场景 | 用到的相关性 | 是否改路由 | 是否有副本 |
|---|---|---|---|---|
| Occult (ICML'25) | 推理 / 微调 | 层内 | ✅ 限制每个 token 的 GPU 数 | ❌ |
| GRACE-MoE (2509.25041) | 推理 | 层内，组大小不等 | ❌ | ✅ |
| ExFlow (IPDPS'24) | 推理（decode） | 跨层 | ❌ | ❌ |
| DeepSeek-V3 node-limited routing | 训练 | — | ✅ | ❌ |
| SmartMoE / MoonEP | 训练 | 无（按负载） | ❌ | MoonEP ✅ |
| **本文** | **从零预训练** | **层内 + 跨层** | ❌ | ❌ |

ExFlow 的跨层亲和不能直接搬到预训练：decode 时 token 可以放在任意方便的 GPU 上，但预训练时 token 要留在持有它那段序列的 GPU 上做 attention，搬动需要额外通信。本文的解决办法是把搬运融合进 SP 已有的 reduce-scatter 里。

## 8. 我的看法（客户沟通 / 落地角度）

1. **对 AWS 场景的意义**：P5/P6 跨节点走 EFA，节点间带宽和节点内差距明显。这正是论文收益最大的情况（跨节点 + 大 top-k）。DeepSeek / Qwen3 / Kimi 这类 top-8 的细粒度 MoE，理论上收益应该更明显。
2. **改动风险低**：数学上和原训练等价，loss 不变，只改通信布局，适合做成可开关的优化。checkpoint 按全局专家 ID 存，可以随时切换摆放方式。
3. **要先验证的点**：
   - 有共享专家、更深（60+ 层）、训练了上万亿 token 的模型上，相关性还有多强？
   - 在 NVLink 全互联的节点内，会不会也出现"最热链路"问题？
   - 能否和 DeepEP 结合？DeepEP 本身就有去重，主要的增量来自摆放和 shuffling。
4. **一个可能的副作用**：路由相关性强，也说明专家之间存在冗余。这和"aux-loss-free 的 loss 最低、但相关性较弱"的现象值得一起思考。
5. **调优抓手**：一个 microbatch 的路由记录就能生成摆放表，成本极低。可以在客户现有的 MoE 训练任务上先离线统计"去重比例"和"跨层命中率"，评估潜在收益后再决定是否改 dispatcher。
