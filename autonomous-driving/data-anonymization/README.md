# 智驾数据脱敏：每天 1 万个 bag 的人脸和车牌打码方案、GPU 估算与 PoC

> 讲解版。读完能回答三个问题：怎么打码？要几张 GPU？怎么验证？

---

## 1. 一句话结论

**对每天 1 万个 bag 做人脸和车牌脱敏，真正的瓶颈是视频编解码和 bag 解析，模型推理反而不是。** 按典型参数（1 分钟 bag、7 路 1080p、10fps）估算，**4–8 张 RTX PRO 4500（g7.4xlarge / g7.8xlarge）** 就能做到 T+1。架构用 S3 → SQS → GPU Worker（可用 Spot）。这个数字目前是估算，偏差可能在 2–3 倍之间，要用单卡压测校准。

**类比**：像邮局给信封盖章。盖章（推理）只要 1 秒，拆信封、再封回去（解码和编码）占了大部分时间。所以要提速，先优化拆封流水线，不用急着换更快的印章。

---

## 2. 处理什么、不处理什么

| 数据 | 是否脱敏 | 说明 |
|---|---|---|
| 相机图像里的人脸 | ✅ 必须 | GDPR 和中国个保法都把人脸算个人信息 |
| 车牌 | ✅ 必须 | 同上 |
| 车内摄像头、音频 | ✅ 必须 | 驾驶员和乘客隐私 |
| GPS / 轨迹 | ⚠️ 看地区 | 在中国属于敏感数据，可能需要坐标偏转，或交给有测绘资质的一方处理 |
| 激光点云 | ⚠️ 评估 | 一般不含可识别人脸，但如果涉及高精地图要单独评估 |
| 其他 topic（CAN、IMU 等） | ❌ 原样保留 | 写回 bag 时保持不变 |

**原则：宁可多打，不能漏打。** 阈值调低、框外扩，误检可以接受。漏检是合规事故，误检只是损失一点训练数据。

## 3. 架构

```
 S3 原始桶 ──(S3 Event)──► SQS ──► GPU Worker 集群（ASG 或 EKS+Karpenter，Spot）
                            │              │
                            │   ┌──────────┴───────────────────────────────┐
                            │   │ ① 解 bag（CPU，rosbag/mcap）              │
                            │   │ ② NVDEC 硬解码 H.264/H.265               │
                            │   │ ③ 人脸+车牌检测（TensorRT FP16，批量）    │
                            │   │ ④ GPU 上做模糊/马赛克                     │
                            │   │ ⑤ NVENC 重新编码，写回 bag（其他 topic 不动）│
                            │   └──────────┬───────────────────────────────┘
                            ▼              ▼
                          DLQ ──► 重试/人工复核      S3 脱敏桶 (+ 处理清单/审计日志)
```

**为什么这样设计**

| 设计 | 原因 |
|---|---|
| SQS 解耦 | bag 之间互不依赖，天然可以并行。失败了自动重投，超过次数进 DLQ |
| Spot | 批处理能容忍中断，消息没 ack 会自动回队列，成本能降 60–70% |
| NVDEC/NVENC | 如果用 CPU 编解码 7 路 1080p，16 核都不够。GPU 有专门的编解码硬件，不占 CUDA 核 |
| 全程在 GPU 显存里处理 | 避免解码后拷回 CPU 再拷回 GPU，PCIe 来回传输会拖慢速度 |
| 选 g7.4xl/8xl，不选 2xl | 2xlarge 只有 8 vCPU，解 bag 和打包时 CPU 会先成为瓶颈 |
| 不选 g7e | 检测模型很小，用不到 96GB 显存，花这个钱不划算 |

## 3.1 bag 怎么处理：拆开 → 只改图像 → 重新打包

不在原 bag 上直接修改，而是**生成一个新 bag**。原始 bag 留在原始桶里，收紧权限，或者按保留策略删除。

**类比**：快递分拣。拆开包裹后，只有"照片"这一类件要过打码机，其余的件（雷达、IMU、CAN）原样放回。最后按原来的顺序和时间戳重新装箱，收件人拿到的包裹和原来格式完全一样。

```
原始 bag ──逐条读消息──┬─ 图像 topic ──► 解码 → 检测 → 打码 → 编码 ──┐
                      │                                              ├──► 按原时间戳写入新 bag
                      └─ 其他 topic（激光雷达/IMU/CAN/tf…）原样拷贝 ──┘
```

**要点**

| 环节 | 做法 | 为什么 |
|---|---|---|
| 读 | 流式逐条读取，不把整个 bag 解压到磁盘 | 省磁盘和 IO，单个 bag 可能有几个 GB |
| 只动图像 topic | 只处理 `sensor_msgs/Image`、`CompressedImage`、视频 topic，其余消息按字节原样拷贝 | 用不着改的就不碰，避免引入错误 |
| 保留时间戳 | 写回时沿用原来的 log time 和 header.stamp，消息顺序不变 | 下游做多传感器时间同步、标注、回放都依赖它 |
| 编码格式和原来一致 | 原来是 JPEG 就写回 JPEG，原来是 H.264/H.265 就重新编码成同样格式 | 下游解析代码不用改 |
| 元数据不变 | topic 名、消息类型、frame_id、相机内参（camera_info）都不改 | 新 bag 可以直接替换旧 bag |

**图像有三种存储方式，处理难度不一样**

| 存法 | 处理方式 | 难度 | 画质 |
|---|---|---|---|
| 原始 Image（未压缩） | 改完像素直接写回 | ⭐ 最简单 | 无损，但 bag 体积大 |
| CompressedImage（每帧一张 JPEG/PNG） | 每帧单独解码、打码、再编码 | ⭐⭐ | 多一次 JPEG 压缩损失，质量参数 ≥90 时基本看不出来 |
| 视频流（H.264/H.265，比如 MCAP 里的 CompressedVideo） | 按 GOP（关键帧开头的一组帧）整段解码再重编码，关键帧位置和帧数要和原来对齐 | ⭐⭐⭐ 最麻烦 | 有重编码损失。用 GPU 的 NVDEC/NVENC 最合适 |

> 视频流比较麻烦的原因是帧之间互相依赖，P 帧和 B 帧只记录和前后帧的差异，所以没法只取出一帧改完再塞回去。

**另一种做法：不放回 bag**
如果下游只拿图像做标注或训练，可以单独输出脱敏后的图像，例如每路相机一个 MP4，再配一份时间戳索引，不重新打包 bag。这样省掉了打包环节，但下游的数据格式要跟着改，具体看客户的工具链怎么定。

**写回后的校验**
- 新旧 bag 逐个 topic 比对消息条数和起止时间戳，必须完全一致。
- 非图像 topic 逐条比对哈希，必须完全相同。
- 抽几帧图像人工看打码效果。每个 bag 的检出数写入处理记录，留作审计。

**先跟客户确认两点**（决定用哪套读写库，压测也按这个格式做）

| 问题 | 可能的值 | 对应的库 |
|---|---|---|
| bag 格式 | ROS1 `.bag` / ROS2 `.db3` / `.mcap` | `rosbags`（纯 Python，三种格式都能读写，不依赖 ROS 环境）/ `mcap` 官方库 |
| 图像存法 | 原始 Image / JPEG / H.264·H.265 | 见上表 |

## 4. GPU 数量估算

**公式**

```
GPU 数 = 每日 bag 数 × 单 bag 处理秒数 ÷ 86400 ÷ 利用率(0.6–0.7)
```

**示例假设**：1 分钟/bag，7 路相机，10fps，1080p，H.264/H.265 压缩。

| 项 | 数值 |
|---|---|
| 单 bag 帧数 | 60s × 10fps × 7 路 = 4,200 帧 |
| 每日总帧数 | 4,200 × 10,000 = 4,200 万帧 |
| 24h 平均需要的吞吐 | ≈ 490 帧/秒 |
| 单卡端到端（解码+检测+打码+编码），估计值 | 150–300 帧/秒 |
| 刚好跑满需要 | 2–4 卡 |
| **留余量（利用率、重试、高峰）** | **4–8 卡** |

**哪些参数会让结果偏差很大（找客户确认）**

1. bag 时长和大小、相机路数、分辨率、帧率、图像格式（压缩视频还是原始 raw/jpeg）
2. 脱敏范围：只做人脸和车牌，还是 GPS 和点云也要处理
3. 时效要求：T+1，还是落盘后几小时内
4. 数据所在 Region（决定能不能就近用 g7，有没有容量）

> 如果是 raw 图像而不是压缩视频，就没有解码开销了，但 IO 和存储量会大很多。如果是 4K 或 30fps，帧数要再乘以 3–4。

## 5. 模型选型

| 方案 | 人脸 | 车牌 | 优点 | 注意 |
|---|---|---|---|---|
| **PoC 用的** | YuNet (OpenCV) | open-image-models YOLOv9-t | 体积小，ONNX 开箱即用，CPU 也能跑 | 不是针对行车视角训练的，远处小目标容易漏 |
| **生产推荐** | Meta **EgoBlur** | EgoBlur | 专门针对第一视角和行车数据训练人脸和车牌 | 确认许可证是否允许商用 |
| 备选 | SCRFD / RetinaFace | YOLO 系车牌模型 | 生态成熟，容易转 TensorRT | 需要自己用行车数据微调 |

模型选定后要转成 **TensorRT FP16**，多路帧合成 batch 一起推理。

## 6. CPU PoC 结果

本机：4 核 CPU，无 GPU，onnxruntime CPU 推理。

| 测试图 | 检出 | 人脸耗时 | 车牌耗时 | 效果 |
|---|---|---|---|---|
| 车辆图（518×331） | 车牌 1 | 9ms | 40ms | 主车牌完全不可读；左侧白车有一块残缺车牌**漏打** |
| 人物图（1280×720） | 人脸 3 | 52ms | 38ms | 两张脸都打上了；有 1 处误检在手部；头发和耳朵覆盖不全，模糊强度偏弱 |
| 街景图（810×1080） | 人脸 2 | 37ms | 35ms | 两人打上了；画面**边缘半个头漏检** |

**结论**
- 流程可行，CPU 上每张图约 80ms。
- 问题集中在**边缘截断目标**和**小目标**的漏检，模糊强度也偏弱，需要改进：
  1. 换 EgoBlur 或行车数据微调过的模型；
  2. 阈值从 0.6 降到 0.3–0.4，框外扩从 15% 调到 25–30%；
  3. 高斯模糊换成**马赛克或纯色填充**，不可逆，审计时也更好说明；
  4. 对图像边缘区域做补边（padding）后再检测。

## 8. GPU 压测计划（下一步）

在 **g7.4xlarge × 1** 上用一个真实 bag 或公开数据集（nuScenes / KITTI）测：

| 步骤 | 测什么 | 工具 |
|---|---|---|
| 1 | 只解码的吞吐 | `ffmpeg -hwaccel cuda` / PyNvVideoCodec |
| 2 | 只推理的吞吐（不同 batch） | TensorRT `trtexec --fp16` |
| 3 | 端到端吞吐 | 解 bag → NVDEC → TRT → 打码 → NVENC → 写 bag |
| 4 | 资源画像 | `nvidia-smi dmon`（看 SM / enc / dec 利用率）、CPU 使用率 |
| 5 | 反推卡数 | 把实测帧/秒代入第 4 节公式 |

判断瓶颈：dec/enc 利用率接近 100% 说明卡在编解码，可以多开几路或换卡；CPU 跑满就换 8xlarge；SM 利用率高就调 batch 或用 INT8。
