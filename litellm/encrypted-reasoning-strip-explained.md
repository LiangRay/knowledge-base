# 为什么要在 LiteLLM 里丢弃 GPT 的加密 reasoning（讲解版）

> 日期：2026-11-12
> 用途：对外讲解 / 培训。技术细节、配置步骤、实测数据见 [gpt-encrypted-content-cross-provider.md](gpt-encrypted-content-cross-provider.md)（方案五）。

讲解顺序：**问题怎么来的 → 为什么删掉就能解决 → 为什么在网关里删 → 代价是什么 → 什么时候不用删**。

## 一句话版本

GPT 推理模型每轮的"思考过程"会加密后交给客户端保管，**只有签发它的那个后端解得开**。网关做负载均衡时，下一轮可能被分到另一个后端，对方解不开就报 400。所以在 LiteLLM 转发前把这段加密内容删掉，任何后端都能接着处理。代价是模型看不到上一轮的思考过程，要重新想一遍。

## 1. 加密块是什么

推理模型（GPT-5.6、GPT-6 等）用 Responses API 时，如果设置了 `store:false`（服务端不保存对话），每轮输出里除了回答和工具调用，还有一项：

```json
{"type": "reasoning", "encrypted_content": "gAAAAB...（几千个字符）"}
```

- 它是模型这一轮的**内部思考过程**，比如"先查天气，再判断适不适合跑步"。
- 服务端不保存对话，所以把思考过程**加密后交给客户端保管**。下一轮客户端（Codex 等）原样带回，模型解开后就能接着上次的思路往下做。
- 加密是为了不让客户端看到原始思考内容。**密钥按加密域划分**：OpenAI 每个 org 一套，Azure 每个 resource 一套，Bedrock 每个 AWS 账号一套。

> 比方：这是一张**盖了公司公章、封了口的草稿纸**，只有本公司的人能拆开看。

## 2. 负载均衡为什么会出问题

```
第 1 轮  客户端 → LiteLLM → 后端 A    A 返回：回答 + 工具调用 + 【A 加密的草稿】
第 2 轮  客户端带着【A 的草稿】→ LiteLLM 轮询分到 → 后端 B
         B：这不是我签发的，解不开 → 400 invalid_encrypted_content ❌
```

- LiteLLM 不知道请求里有这段密文，按正常方式轮询、随机或故障切换到另一个后端。
- 客户端每轮都会把历史原样带回，**只要中途换过一次后端，这个会话后面就一直失败**。
- 实测：不加处理时，8 次回放中落到另一个后端的 4 次全部 400（`The encrypted content could not be verified ... organization_id did not match`）。

## 3. 为什么删掉就能解决（核心）

关键在于：**草稿只是辅助，对话本身并不缺东西**。

客户端每轮带回的完整历史：

| 内容 | 是否加密 | 删掉后 |
|---|---|---|
| 用户问题 | 明文 | 保留 |
| 模型调了什么工具、参数是什么（`function_call`） | 明文 | 保留 |
| 工具返回了什么（`function_call_output`） | 明文 | 保留 |
| 模型之前的回答 | 明文 | 保留 |
| **思考过程（`reasoning`）** | **加密** | **删掉** |

删掉之后，新后端看到的是一段**完整、自洽的明文对话**：用户问了什么、调了哪些工具、拿到了什么结果。它完全可以接着做，只是不知道上一轮"心里怎么想的"，需要根据明文重新推理一遍。

> 比方：换了个人接手，草稿纸打不开就扔掉。题目、已经算出的中间结果都写在明面上，新人看一遍就能接着算。

实测：删掉后，换到另一个后端也全部 200，多轮工具调用 8 组全部跑通。

## 4. 为什么在网关（LiteLLM hook）里删，而不是让客户端改

- **客户端改不了**：Codex 这类工具是现成的，设计上就是把 reasoning 原样带回。
- **客户端也不知道该不该删**：它看不到网关把请求转给了哪个后端，只有网关知道。
- **改一处就能覆盖所有客户端**：所有用户和工具都经过 LiteLLM，在这里统一处理最省事。
- **钩子位置**：`async_pre_call_hook` 是 LiteLLM 在"收到请求、还没转发"时调用的钩子，可以在这里改请求内容。十来行代码：遍历 `input`，去掉 `type == "reasoning"` 的项，然后放行。代码见 [hooks/strip_all_reasoning.py](hooks/strip_all_reasoning.py)。

## 5. 代价（要讲清楚，不能只讲好处）

"全扔"是**无差别删除**：就算下一轮还落在同一个后端（本来解得开），也删掉了。

1. **推理连续性变差**：模型每轮都要重新想。简单任务基本看不出区别，长链路、复杂的多步任务可能质量下降或步骤变多。OpenAI 官方建议推理模型做工具调用时把 reasoning 带回去。
2. **Prompt Cache 命中可能下降**：请求前缀变了。
3. **输入 token 会少一点**：思考过程不再重复发送。实测 141 → 122，算是个小副作用。

所以还有升级版 **5b（软亲和 + 按需删）**，代码见 [hooks/encrypted_reasoning_guard.py](hooks/encrypted_reasoning_guard.py)：

- 下一轮**优先分回原后端**，这时保留 reasoning，效果和不加网关一样。
- 只有原后端挂了、必须换后端时，才删掉"别家签发的"那部分。

| | 5a 全扔 | 5b 软亲和 + 按需删 |
|---|---|---|
| 代码量 | ~15 行 | ~140 行 |
| 解密报错 | 不会 | 不会 |
| 推理连续性 | 每轮都丢 | 同后端保留，仅切换时丢 |
| 实测 | 回放 8/8 成功 | 回放 8/8、多轮 8/8、流式 5/5 成功 |
| 待验证 | — | 原后端宕机时的切换路径 |

为什么不直接用 LiteLLM 自带的 `encrypted_content_affinity`：它是"硬绑定"，原后端不可用时直接返回 429/503，**不会切换到别的后端**，起不到故障切换的作用。

## 6. 什么时候根本不需要删

加密边界是"加密域"，**不是 Region**：

- 同一个 AWS 账号下，Bedrock us-east-1 签发的密文拿到 us-east-2 也能解开（实测 200）。**只在同一账号内做 Bedrock 多 Region 负载均衡，不需要这个 hook。**
- 需要删的场景：多个 OpenAI org、多个 Azure resource、多个 AWS 账号，或者 Bedrock 和 OpenAI/Azure 混用。

## 讲解用示意图

```
               ┌── 后端 A（签发者，能解）
客户端 ── LiteLLM ┤
   带回加密草稿    └── 后端 B（解不开 → 400）

加 hook 后：
客户端 ── LiteLLM【删掉加密草稿，只留明文历史】── 任意后端都能接着做 ✅
```
